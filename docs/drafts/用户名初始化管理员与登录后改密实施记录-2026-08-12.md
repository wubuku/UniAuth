> 状态：Completed
> 日期：2026-08-12
> 当前事实入口：[当前架构](../ARCHITECTURE.md)、[配置基线](../CONFIGURATION.md)、
> [前后端契约](../FRONTEND_BACKEND_CONTRACT.md)

## 1. 问题与结论

UniAuth 原有 `POST /api/auth/login` 已支持 `LOCAL` 用户名/密码登录；邮箱注册账户也以
邮箱作为 `local_username`，因此邮箱/密码登录同样走该入口。缺口不在登录验证本身，
而在以下两个闭环：

1. 默认没有一个安全、显式、可重复部署的初始化管理员账号机制。
2. 已登录的本地账号没有验证当前密码后自行修改密码的受支持 API 和前端入口。

本轮不开放普通用户自选用户名注册的新流程，也不改变 OAuth2、Web3、邮箱注册和密码
重置语义。

## 2. 固定实施范围

### 2.1 初始化管理员

- 新增默认关闭的 `app.bootstrap-admin` 配置。
- 只有显式提供 enabled、username、email 和通过当前策略的 password 时才创建账号。
- 新账号具有 `ROLE_USER + ROLE_ADMIN`，并拥有 verified primary `LOCAL` 登录方式。
- 重复启动只验证既有账号，不覆盖已有密码。
- 用户名、邮箱、本地用户名映射到不同用户，或既有账号缺少管理员权限/本地密码时，
  启动失败关闭。
- 不内置固定 `admin/password`，不读取或记录真实部署密码。

### 2.2 登录后修改密码

- 新增受 Resource Server 保护的 `PUT /api/user/password`。
- 只修改 JWT 当前用户自己的 `LOCAL` 密码。
- 要求 recent-auth、当前密码、新密码策略和确认值。
- 密码 hash 更新使用 PostgreSQL 条件 CAS，不使用悲观锁。
- 成功后递增 token security version、撤销全部 token family、记录安全事件并清理
  access/refresh/Session 认证 Cookie。
- 旧 access/refresh token 立即失效，用户必须使用新密码重新登录。

### 2.3 前端

- canonical current-user 响应增加 `hasLocalPassword`。
- 只有该值为 `true` 时显示“修改密码”入口。
- 修改成功后清除本地诊断认证状态，并跳回登录页显示明确成功提示。
- 纯 OAuth2/Web3 或 passwordless `LOCAL` 用户不显示入口。

## 4. 安全与兼容决策

- 初始化账号与 disposable demo data 相互独立；默认都不创建固定管理员凭据。
- 配置密码只在启动时用于首次 BCrypt hash，不进入日志、响应或文档。
- 改密不是密码重置：必须提供当前密码，且 recent-auth 过期时拒绝。
- CAS 失败返回稳定 `409`，不会让并发请求静默覆盖。
- security version 递增与密码 hash 更新处于同一事务；后续状态更新失败会回滚改密。
- `hasLocalPassword` 只在 `LOCAL` hash 非空且非空白时为 true。
- 本轮不修改已发布 Flyway V1-V8；现有 schema 已具备所需字段和索引。

## 5. 验收矩阵

| 场景 | 预期 |
|------|------|
| 默认配置启动 | 不创建初始化管理员 |
| 显式配置首次启动 | 创建可用用户名/密码管理员和两项角色 |
| 重复启动 | 不覆盖已经修改的密码 |
| 弱初始化密码/身份冲突 | 启动失败关闭 |
| 错误用户名或密码 | `401` |
| 初始化管理员用户名登录 | 成功签发当前 token family |
| 错误当前密码 | `401 CURRENT_PASSWORD_INVALID` |
| 新密码确认不一致 | `400 PASSWORD_CONFIRMATION_MISMATCH` |
| Cookie + CSRF 修改密码 | `200`，清理认证 Cookie |
| 修改密码后的旧 access/refresh | Resource Server、refresh、introspection 均拒绝 |
| 新密码登录 | 成功 |
| 纯 OAuth2/Web3 当前用户 | 前端不显示修改密码入口 |
| 并发改密 | 只有一个 CAS 成功，竞争请求返回 `409` |
